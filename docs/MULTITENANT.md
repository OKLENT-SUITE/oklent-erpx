# تعدد العملاء (Multi-tenant) — الإصدار 1.5.0

## التصميم: مخطط PostgreSQL مستقل لكل عميل
كل عميل = **مخطط (schema) خاص `t_<الرمز>`** يحوي نسخة كاملة من الجداول والقواعد والدوال. لذلك:

- سلسلة تجزئة القيود، وعدّاد الفواتير ICV/PIH، وقيد «صف واحد للشركة»، ورموز الحسابات — **مستقلة لكل عميل بالبناء**، دون عمود `tenant_id` ودون المساس بأي استعلام.
- لا يمكن لخطأ في استعلام أن «يخلط» عميلين: الاتصال نفسه يُفتح و`search_path` مضبوط على مخطط العميل.
- النسخ الاحتياطي والاستعادة والتصدير والحذف **لعميل واحد** عملية بسيطة (`scripts/tenant-backup.sh`).
- التركيب القائم لا يتحرك: بياناته في `public` وتُسجَّل كـ «الشركة الافتراضية» (`is_default`).

| الطبقة | الملف | الدور |
|---|---|---|
| سجل العملاء | `db/platform/001_platform.sql` (`platform.tenants`, `tenant_events`) | الحالة: provisioning / active / suspended / archived / failed. التطبيق **يقرأ فقط** |
| ترجمة SQL | `api/src/tenant-sql.js` | يترجم ملفات `db/init` لمخطط العميل ويرفض أي ملف يبقي إشارة صريحة لـ `public` |
| الإنشاء/الإيقاف | `api/src/tenant-admin.js` + `tenant-cli.js` | بصلاحية المالك فقط (معاملة واحدة: إما اكتمل أو لا شيء) |
| السياق والاتصالات | `api/src/tenancy.js` + `db.js` | سياق لكل طلب (AsyncLocalStorage) ومجمّع اتصالات لكل عميل `search_path` ثابت عند الاتصال |
| الترقية | `api/src/migrate.js` | يرقّي كل المخططات؛ فشل عميل لا يوقف البقية ولكن يوقف الحزمة (`exit 1`) |
| الملفات | `api/src/uploads.js` | `/uploads/t/<الرمز>/products/` ولا يحذف عميل ملف غيره |

## طبقات الحماية (فشل مغلق)
1. **الهوية من التوقيع لا من العنوان:** عميل الطلب المسجَّل دخوله يأتي من حقل `tid` في JWT الموقَّع؛ لا يغيّره `Host` ولا `X-Tenant`.
2. `q()` و`tx()` **ترميان خطأ** إن لم يوجد عميل في السياق (لا رجوع صامت إلى `public`).
3. `tx()` يتحقق من `current_schema()` قبل أي كتابة.
4. الدوال `SECURITY DEFINER` تُترجم بـ `search_path = "t_x", public, pg_temp` (public لأجل pgcrypto فقط).
5. تعليق عميل يقطع جلساته خلال ≤ 15 ثانية (`TENANT_CACHE_TTL_MS`).
6. اختبار آلي يمنع أي ملف SQL جديد فيه `public.` صريحة (`tests/tenant-unit.mjs`).
7. تحديد المعدل لمحاولات الدخول يُفتَّح بـ (العميل + المستخدم).

## التشغيل
```bash
# 1) فعّل الميزة ورقِّ قاعدة البيانات (يسجّل البيانات الحالية كشركة "default")
echo "MULTI_TENANT=1" >> .env
docker compose -f docker-compose.prod.yml up -d --build

# 2) أنشئ عميلاً (يطبع كلمة مرور المدير مرة واحدة إن لم تحددها)
docker compose -f docker-compose.prod.yml --profile admin run --rm tenant-admin create \
   --slug acme --name "شركة أكمي" --vat 300000000000003 --cr 1010000000 --email ops@acme.com --max-users 25

# 3) إدارة
... tenant-admin list | verify | suspend --slug acme --reason "عدم السداد" | resume --slug acme | archive --slug acme | set-domain --slug acme --domain erp.acme.com
```
**كيف يصل العميل إلى نظامه** (بالترتيب): نطاق مخصص ← نطاق فرعي (`TENANT_BASE_DOMAIN=erp.example.com` ثم `acme.erp.example.com`، يلزم DNS ‎`*.erp.example.com` وشهادة wildcard) ← حقل «رمز الشركة» في شاشة الدخول ← `/t/acme/shop/store` للمتجر العام. `TENANT_REQUIRE_EXPLICIT=1` يمنع الرجوع للشركة الافتراضية.

## ما لا يمكن أن يُنجز من داخل الحزمة (جاهز ويحتاج قراراً/بنية)
| البند | الحالة | المطلوب منك |
|---|---|---|
| إنشاء عميل من واجهة ويب/اشتراك ذاتي | **مجهّز لا منفَّذ**: لأن التطبيق لا يملك صلاحية المالك عمداً | شغّل `tenant-admin create` من لوحة أعمالك/Webhook الدفع، أو أضف خدمة `provision` خلف شبكة داخلية |
| شهادة wildcard ونطاقات العملاء | يحتاج نطاقاً | `*.erp.example.com` عبر certbot DNS-01 |
| PgBouncer | غير مدعوم في وضع transaction (يُسقط خيارات الاتصال) | استخدم session pooling أو الاتصال المباشر |
| عدد العملاء لكل خادم | **غير مقاس** | اختبر الحمل (`max_connections` ≈ عدد المخططات النشطة × `PG_TENANT_POOL_MAX`؛ الحد الافتراضي 40 مجمّعاً نشطاً `PG_MAX_TENANT_POOLS`). فوق بضع مئات من العملاء قيّم تقسيمهم على أكثر من قاعدة |
| استعادة عميل واحد | سكربت جاهز غير مجرَّب على قاعدة حقيقية | نفّذ تمرين استعادة شهرياً |
| تسعير/حدود الخطة (`plan`, `max_users`) | مخزّنة ولا تُفرض بعد على الواجهة | `max_users` يُفرض عند إنشاء المستخدمين: تنفيذ لاحق |
| حذف نهائي لعميل | لا أمر `drop` عمداً | `archive` ثم صدّر ثم `DROP SCHEMA ... CASCADE` يدوياً بعد موافقة مكتوبة |

## حدود معروفة (صراحةً)
- **لم تُشغَّل اختبارات قاعدة البيانات على الجهاز الذي بُنيت عليه** (لا PostgreSQL ولا Docker ولا شبكة). المُتحقَّق منه محلياً: الترجمة الآلية لكل ملفات SQL، حلّ العميل، عزل الملفات، TOTP، الحراسات الساكنة. أما `tests/tenant-isolation.mjs` (إنشاء عميلين فعلياً، العزل، الإيقاف، 2FA) فيعمل ضمن `npm run test:all` على جهاز فيه PostgreSQL، **وهو أول ما يجب تشغيله**.
- جداول `sa_regions/sa_cities/...` (الجغرافيا) تُنسخ لكل عميل (حجم صغير؛ مفيد لأن العميل قد يضيف مدناً).
- ملفات `db/init` الجديدة مستقبلاً يجب ألا تحوي `public.` صريحة وإلا فشل الاختبار.
