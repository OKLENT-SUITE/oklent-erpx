# ZATCA — المرحلة الثانية: ما هو جاهز وما يحتاج حسابك (العيبان 1 و2)

> **الحالة: مجهّزة وغير معتمدة.** لا تسوّق النظام «متوافقاً مع المرحلة الثانية» قبل اجتياز **قائمة القبول** أدناه على بيئة الهيئة.

## منجز ومُتحقَّق منه محلياً (`node tests/zatca2-unit.mjs`)
| المكوّن | الملف | التحقق |
|---|---|---|
| تطبيع C14N (شامل، يعادل 1.1 لهذه المستندات) ومحلّل XML آمن (يرفض DTD) | `api/src/zatca2/c14n.js` | متجهات اختبار + رفض المشوّه |
| تجزئة الفاتورة وفق الهيئة (استبعاد UBLExtensions وcac:Signature ومرجع QR) | `c14n.js: invoiceHash` | ثابتة، تتغير بأي تعديل، **تختلف عن `xmlHash` القديم** (علاج العيب 2) |
| توقيع XAdES-BES (ECDSA secp256k1 + SHA-256) وتضمينه | `sign.js` | توقيع ثم تحقق مستقل؛ كشف العبث بالمبلغ/التوقيع/استبدال الشهادة |
| رمز QR بالوسوم 1–9 | `qr.js` | فك TLV ومطابقة التجزئة والتوقيع |
| طلب الشهادة CSR (secp256k1, قالب الهيئة, SAN) | `csr.js` | يُنشأ ويُتحقق بـ openssl |
| عميل منصة فاتورة (compliance, production CSID, reporting, clearance) | `onboarding.js` | **ضد بوابة وهمية فقط**؛ معطّل ما لم `ZATCA_ENABLED=1` |
| تخزين الاعتماديات والإرسالات (مفاتيح مشفّرة AES-GCM) | `db/init/300_zatca_phase2.sql` | ضمن اختبار الترجمة لكل عميل |

## لا يمكن إنجازه دون طرفك أو الهيئة
| # | المطلوب | من يملكه |
|---|---|---|
| 1 | تسجيل المنشأة في بوابة فاتورة والحصول على **OTP** | أنت/العميل |
| 2 | تشغيل **Compliance CSID** ثم **Production CSID** (`onboarding.js`) | يحتاج #1 + شبكة |
| 3 | **التحقق بمدقّق SDK الرسمي** ونماذج الهيئة (XSD + Schematron) على فواتير نظامك | حمّل الـ SDK من بوابة الهيئة (غير متاح هنا) |
| 4 | **تأكيد 3 تفاصيل بحسب نماذج الـ SDK** (نُفِّذت بحسب فهمنا للمواصفة): (أ) تشفير `CertDigest`/`SignedProperties` = base64 لـ hex؛ (ب) ترتيب مكوّنات IssuerName؛ (ج) أي عناصر UBL إلزامية ناقصة في `buildUbl` (وسوم عنوان البائع، `cbc:Note`، `PaymentMeans`، `TaxSubtotal`، `ActualDeliveryDate`، رمز السبب في الإشعارات) | اختبار مقابل الـ SDK |
| 5 | ربط الإصدار: عند `issueInvoice` يُنشأ XML ثم **يُوقَّع** ثم يُسجَّل في `zatca_submissions` ويُرسل (مبسّطة: Reporting خلال 24 ساعة؛ قياسية: Clearance قبل التسليم) | **غير موصول عمداً** حتى لا يتغيّر مسار الفوترة الحالي قبل اجتياز #3 |
| 6 | حفظ المفتاح الخاص: `sealSecret()` الآن؛ للإنتاج الجاد استخدم KMS/HSM | قرار تشغيلي |
| 7 | إعادة الإرسال عند فشل الشبكة وعمّال الخلفية (queue) | يُبنى بعد #5 |

## قائمة القبول (كلها يجب أن تنجح قبل أي ادعاء)
- [ ] CSR أُنشئ ولُصق في بوابة المطوّر وأُصدر Compliance CSID (sandbox).
- [ ] فواتير الاختبار الستة (قياسية/مبسطة × عادية/دائن/مدين) اجتازت `/compliance/invoices` بلا أخطاء.
- [ ] مدقّق SDK المحلي يقبل XML الموقَّع (`fatoora -validate`) بلا أخطاء وبتحذيرات مفهومة.
- [ ] Production CSID في بيئة المحاكاة، ثم فاتورة Reporting وأخرى Clearance ناجحتان.
- [ ] سلسلة ICV/PIH متصلة بعد الفواتير الموقَّعة (PIH = تجزئة الفاتورة الموقَّعة السابقة بحسب الهيئة).
- [ ] اعتماد كتابي من المالك: «المرحلة الثانية معتمدة» ← عندها فقط يُحدَّث `README` و`docs/legal/terms`.

## التفعيل (بعد اجتياز القبول)
`ZATCA_ENABLED=1` و`ZATCA_ENV=simulation|production` ثم وصل خطوة التوقيع/الإرسال (البند 5).
