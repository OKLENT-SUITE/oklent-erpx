# دراسة تطوير المساعد المحلي والوكيل التحليلي

التاريخ: 2026-10-23  
نسخة التطبيق المستهدفة: 1.4.0

## خلاصة القرار

أفضل مسار لهذا التطبيق هو وكيل تحليلي محلي مضبوط بالسياسات، وليس نموذجاً يكتب SQL حراً أو يملك أدوات تنفيذ عامة. المحرك الحالي فيه PostgreSQL، أدوار مستخدمين، دوال تقارير محاسبية موثوقة، وسجلات عمليات حساسة. لذلك يكون الترتيب الآمن: فهم طلب محدود → اختيار تقرير/نية من قائمة مسموحة → استدعاء استعلام مجمّع ثابت بمعاملات → فحص شكل النتيجة → صياغة تفسير محدد → إخراج مخطط مرئي. لا تُمنح طبقة الفهم اتصالاً مباشراً بقاعدة البيانات ولا وسائل تغيير البيانات.

الإصدار 1.4.0 يفعّل المساعد المحلي تلقائياً، ويضيف ملخصات المخزون والفواتير والأسطول وأعمار الذمم والمركز المالي والإقرار الضريبي، ويعرض مخططات SVG وبطاقات مؤشرات وجداول بديلة. لا يحتاج مفتاحاً أو عنوان خدمة، ولا يستدعي خدمة خارج التطبيق.

## منهج البحث

راجعت بنية التطبيق والواجهات الحالية وقاعدة البيانات، خصوصاً `invoices`, `invoice_lines`, `invoice_payments`, `journal_entries`, `journal_lines`, `accounts`, `products`, `stock_moves`, `product_costing`, `online_orders`, `employees`, `payroll_runs`, `expense_claims`, وجداول الأسطول والحجوزات والعقارات. كذلك راجعت دوال التقارير: `fn_trial_balance`, `fn_income_statement`, `fn_balance_sheet`, `fn_vat_return`, `fn_ar_aging`, و`fn_general_ledger`.

تؤكد إرشادات OWASP أن ربط مدخل المستخدم بنص SQL خطر، وأن معاملات الربط وقوائم السماح أقل عرضة للحقن. وتوضح وثائق PostgreSQL أن سياسات RLS تستطيع فرض تصفية صفوف على مستوى قاعدة البيانات، لكنها تتطلب سياسات صحيحة ومراجعة امتيازات الأدوار. وتبين أبحاث تقييم Text-to-SQL أن الدقة تتراجع عند الانتقال إلى مخططات وأسئلة خارج بيانات التدريب؛ لذلك لا يكفي أن يبدو SQL الناتج صحيحاً. أما Vega-Lite فيقدم مواصفة مرئية معلنة تصلح لبناء الرسوم التحليلية، لكن هذا الإصدار يرسم SVG محلياً كي يبقى مستقلاً عن الشبكة والمكتبات الخارجية.

## خريطة الميزات على جداول النظام

| المجال | الجداول / دوال التقرير | الإخراج المقترح | سياسة الإتاحة |
|---|---|---|---|
| المالية | `journal_entries`, `journal_lines`, `accounts`, `fn_trial_balance`, `fn_income_statement`, `fn_balance_sheet` | اتجاه شهري، دخل، ميزان، مركز مالي | ملخصات مجمعة؛ منع القيد أو الترحيل |
| الفواتير والتحصيل | `invoices`, `invoice_lines`, `invoice_payments`, `fn_invoice_outstanding`, `fn_ar_aging` | إجمالي/متبقي، أعمار الذمم، مقارنة الفترات | دون أسماء العملاء في لوحات التحصيل العامة |
| الضريبة | `tax_codes`, `fn_vat_return` | صافي ومخرجات ومدخلات الضريبة | ملخص الفترة؛ التنبيه أن المساعد لا يقدم اعتماداً ضريبياً |
| المخزون | `products`, `stock_moves`, `product_costing`, دوال التوفر والحجز | كمية وقيمة ونفاد المخزون واتجاه الحركة | قراءة فقط؛ القيمة وفق تكلفة المتوسط المسجلة |
| البيع الإلكتروني | `online_orders`, `online_order_lines`, `stores` | عدد الطلبات وحالتها واتجاه المبيعات | لا يفصح عن العنوان أو الهاتف في الملخصات |
| الأسطول | `fleet_vehicles`, `fleet_trips`, `fleet_fuel`, `fleet_maintenance` | تكلفة، مسافة، استهلاك وقود، صيانة قريبة | إظهار بيانات المركبة بحسب صلاحية الشاشة |
| الحجوزات والعقارات | `bookings`, `booking_lines`, `properties`, `units`, `leases`, `rent_schedule` | إشغال، حجوزات، إشعارات إيجار مستحقة | لا يغيّر حالة الحجز أو العقد |
| الموارد البشرية | `employees`, `payroll_runs`, `payroll_items`, `expense_claims`, `custodies` | مؤشرات عددية أو تشغيلية حسب الدور | بيانات الرواتب والهوية الحساسة محجوبة عن المساعد العام؛ تحتاج أدوار HR/Finance صريحة ومراجعة تدقيق مستقلة |

## ما تم تطبيقه في 1.4.0

1. **المساعد محلي افتراضياً:** تهيئة Compose لا تمرر عنوان مزود أو مفتاح API. مسار التنفيذ لا يستدعي مزود النموذج.
2. **استعلامات محددة:** أنواع التقارير وقيمها قائمة سماح؛ اختيار تلقائي محدود بكلمات عربية/إنجليزية مع خيار التحديد اليدوي؛ SQL مكتوب في الخادم ومعاملاته مرتبطة، ولا توجد أداة SQL حرة.
3. **مجالات إضافية:** الذمم المدينة المجمعة حسب التأخير، المركز المالي المجمع، والإقرار الضريبي، بالإضافة إلى الفواتير والمخزون والأسطول وتقارير الدخل والميزان.
4. **مرئيات ذات مصدر موثوق:** الخادم يعيد مخططاً بيانياً منظماً إلى جانب أرقام التقرير. الواجهة تعرض مؤشرات وبارات SVG، قيمها من الاستجابة نفسها؛ لا يُسمح للنص الذي يكتبه المستخدم بإنشاء حقول رسم أو شيفرة HTML/SVG.
5. **إتاحة بديلة:** الرسم له وصف لقارئ الشاشة، ويمكن فتح بيانات الرسم كجدول.
6. **حماية تشغيلية:** حد زمني للفترة، صلاحية دخول وأدوار، حد طلبات، ومراجعة تدقيق لا تحفظ نص السؤال أو الإجابة.

## تصميم الوكيل المقترح على مراحل

### المرحلة 1 — مكتبة أسئلة ومرئيات (مفعّلة الآن)

إضافة تقارير ثابتة بعد مراجعة محاسبية، ووسوم عربية للمؤشرات. لكل تقرير: اسم واضح، وصف ومصدر، معاملات تاريخ، حد نطاق/صفوف، نوع رسم مناسب، وعينة استجابة. هذه المرحلة تحافظ على دقة البيانات حتى دون اتصال خارجي.

### المرحلة 2 — فهم عربي محلي مضبوط

إضافة قاموس عربي/إنجليزي للمقاييس والمرادفات، واستخراج الفترة والفرع والمخزن من السؤال. ينتج المحلل **خطة JSON** لا SQL: `{metric, dimension, period, filters, chart}`. كل قيمة يجب أن تطابق مخططاً معروفاً. السؤال الملتبس يعرض سؤال توضيح أو قائمة خيارات بدلاً من التخمين. يظل التقرير المختار هو مصدر الحساب.

### المرحلة 3 — وكيل أدوات قراءة فقط

إتاحة أدوات خادم ضيقة مثل `summarize_invoices`, `inventory_snapshot`, `fleet_costs`, `trial_balance`. لكل أداة معاملات schema، سقف صفوف، مهلة، صلاحية، ومصدر نتائج. يمنع منح الوكيل `query(sql)`, shell، تصفح ملفات، أو أدوات كتابة. التوسع إلى نموذج لغوي محلي لا يبرر تجاوز هذه الحدود.

### المرحلة 4 — مرئيات تفسيرية وتفاعلية

إضافة مقارنة فترة مقابل الفترة السابقة، تفكيك سبب الفرق، تنبيهات مبنية على قواعد عمل منشورة، drill-down إلى صفحة التطبيق الأصلية بصلاحية المستخدم، وتنزيل CSV/طباعة. لا يُعرض مخطط عندما تكون الوحدة مختلفة أو البيانات ناقصة؛ يُعرض جدول مع تنبيه. إذا زاد تنوع الرسوم، يمكن تجميع Vega-Lite محلياً داخل ملفات التطبيق، دون CDN.

### المرحلة 5 — تعلّم جودة منضبط

قياس نجاح النية، صحة الفترة، تطابق الإجابة مع تقرير النظام، زمن التنفيذ، والنتائج الفارغة. تُحفظ المعرفات والمدة والحالة فقط؛ لا حاجة لتسجيل نصوص الأسئلة أو بيانات شخصية. مراجعة الانحرافات تكون على عينات اصطناعية أو بيانات منزوعة الهوية، مع مقارنة كل تقرير بمصدره المحاسبي.

## قواعد أمنية ومحاسبية لا ينبغي تخفيفها

- لا SQL حر مولد من النموذج. أي فهم لغوي يتحول إلى خطة JSON مسموحة ثم ينفذ عبر دوال أو استعلامات ثابتة.
- حساب قاعدة البيانات لا يحصل على امتيازات أوسع لمجرد تشغيل المساعد. التصفية بحسب الفرع أو الشركة يجب أن تكون جزءاً من صلاحية التقرير، وتُراجع RLS إن كانت المؤسسة تحتاج عزلاً على مستوى الصف.
- معاملات التاريخ والفرع والحساب تُتحقق وتُربط كمعاملات؛ أسماء الجداول والأعمدة وأنواع الرسوم لا تأتي من نص المستخدم.
- لا كشف رواتب/هوية/عناوين أو بيانات اتصال في الردود العامة. يجب تطبيق الدور قبل الاستعلام، لا بعد صياغة الرد.
- الإجابة المالية تعرض الفترة، العملة، وتاريخ الاستخراج ومصدر التقرير. لا يعاد حساب أرقام النظام داخل المتصفح.
- الوكيل لا يرسل فاتورة، لا يعدل مخزوناً، لا يرحّل قيداً، ولا يغير عقداً أو حجزاً. أي إجراء مستقبلي يجب أن يبقى سير عمل منفصلاً بتأكيد مستخدم مخول.

## معايير قبول التطوير القادم

- كل نية موثقة واختبارات تحققها، بما فيها مرادفات عربية، سؤال ملتبس، فترة غير صحيحة، ومحاولة إدخال SQL.
- مطابقة إجمالي الملخص لمخرجات تقرير التطبيق الأصلي على نفس الفترة والفرع.
- لا يتغير أي صف أو قيد أو حركة مخزون بفعل المساعد.
- كل مرئي له مصدر وفترة ووحدة وجدول بديل؛ ولا يعتمد على شبكة CDN.
- اختبارات للأدوار والبيانات الحساسة ومهلات الاستعلام والحد الأعلى للصفوف.
